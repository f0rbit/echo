Plan: design-language — unification + polish pass (echo + forge)

todo

Unify the visual + interaction design language across echo's five playable subsystems and the hub, fix the P0 debug-surface-in-production leak at its root (forge), bring every game to a written quality floor (font, shell screens, HUD, juice, lighting), make new-subsystem setup a copy of a living verified template, and finish with a docs-tightening pass. Companion forge workstream is small, docs-heavy, and ships exactly one behaviour change (debug gate) as v0.6.0. Audit findings from the completed code + screenshot tour are treated as ground truth. All LOC estimates below already include the repo's empirical 2.75x multiplier over naive budgets (AGENTS.md "LOC budgets understate by ~3x").

Root cause

Stated goal: make the five games look/feel coherent and polished, sanity-check forge's API, make new games fast to scaffold, and keep docs aggressively simple.

Underlying need: echo's per-subsystem quality is re-negotiated from scratch each phase because the design language lives in scattered FRICTION entries and one exemplar subsystem (progress), not in a contract. Phase 6 (boss), Phase 7 (hub subsystem) and Phase 8 (main) will each re-diverge unless the language is (a) written down in one page, (b) embodied in a living, CI-verified template, and (c) enforced at the engine boundary where policy belongs (debug gate in forge, not five build scripts). The games are also forge's public demo surface — a deployed debug HUD undermines every other polish item at once.

Why this matters: polishing pixels without codifying the contract means this exact audit repeats after the next subsystem lands. Fixing the debug leak per-subsystem instead of in forge leaves the footgun armed for every future forge consumer (coin-collector already ships it). The root fix is: one contract page + one live template + one engine-side policy point.

Alternatives considered

Two decision areas warrant full option analysis: the P0 debug-in-prod fix (decision A) and the scaffold-speed approach (decision B). The remaining workstream items (pixel-font unification, shell sweep, HUD contract, juice floor, modal fixes, hub thumbnails, docs pass) are direct executions of audit findings with an established in-repo precedent each — no architectural alternatives evaluated for those; the precedent (progress's pixel recipe, arena's shell FSM, progress's ui kit) is cited per task. Market examples below are drawn from primary sources (tool docs, engineering blogs) per the explorer quality bar.

Decision A — killing the debug-surface-in-production leak

Ground truth: is_dev() in forge/src/debug/debug.ts resolves proc?.env?.NODE_ENV !== "production"; in a bun build --target browser bundle there is no process, so it returns true and every deployed echo page ships window.__forge, the palette, and the tick/fps HUD.

Option A1: per-subsystem --define flags in build scripts

Add --define __DEV__=false to every production bun build invocation (5 subsystems x 2-3 entry points each) and --define __DEV__=true to every dev script. No forge change; ships today.

Real-world examples

  • React — dev-only code is guarded by process.env.NODE_ENV and eliminated by the consumer's bundler define; React explicitly documents that the app's build config, not the library, is responsible for setting it. source
  • esbuild — the --define mechanism bun build inherits; documented as the canonical way to burn build-time constants into bundles. source

Pros

  • Zero forge release needed; echo-only change, mergeable in one small PR.
  • Dead-code elimination: debug paths tree-shake out of prod bundles entirely.

Cons

  • ~12 build invocations across 5 package.json files must each carry the flag, forever — progress's build script alone chains 3 bun build calls. One missed flag re-arms the footgun silently.
  • The scaffold template and docs/new-subsystem.md must both teach the flag; drift re-introduces the leak in subsystem #6.
  • Does nothing for other forge consumers (coin-collector is live with the leak).
  • No cheap ?debug=1 prod opt-in — the surface is compiled out.

Option A2: forge-side safe default — explicit-signal resolution + ?debug=1 opt-in

recommended

Rewrite forge's dev-mode resolution as a pure function over explicit signals with precedence: ?debug=1|0 query param > __DEV__ define > NODE_ENV === "development" > localhost/127.0.0.1 hostname heuristic > default false. is_dev() becomes a thin wrapper reading real globals; the pure resolver is unit-tested with in-memory signal objects. Ships as forge v0.6.0; echo's only change is a version bump. Local dev (bun run serve on localhost) stays debug-on with zero config; deployed GitHub Pages goes debug-off; ?debug=1 re-enables the full surface on the live site for agent verification.

Real-world examples

  • Vite — import.meta.env.DEV/PROD are owned by the tool, not by each app; consumers get one canonical signal and cannot mis-wire it per-project. source
  • Sentry SDK — debug: false by default in all SDKs; diagnostic surfaces are explicit opt-in because SDK authors, not app authors, own the safe default. source

Pros

  • Policy lives in exactly one place (forge) — matches the already-documented convention in docs/forge.md; echo, coin-collector, and every future consumer inherit the fix via one bump.
  • ?debug=1 keeps the audit's requirement: prod debug surface reachable via explicit opt-in, which also keeps the __forge screenshot verification recipes working against live pages.
  • localhost heuristic preserves the existing agent workflow (serve-dist + screenshot) with no build-script changes anywhere.
  • Pure resolver is trivially unit-testable — the failure mode that shipped this leak becomes a compile-adjacent test.

Cons

  • Behaviour change requires a forge release (v0.6.0) before echo can consume it — echo phase 3 blocks on npm publish.
  • No dead-code elimination: debug code stays in prod bundles (gated off at runtime). Bundle-size cost is tolerable for game pages; BootOpts docs already claim tree-shake-out only when debug: false is passed explicitly, which no echo subsystem does today anyway.
  • BREAKING for consumers relying on implicit debug-on in browser bundles — which is precisely the bug.

Architecture decisions

  • Debug-gate precedence (decision A): ?debug=1|0 > __DEV__ define > NODE_ENV === "development" > localhost/127.0.0.1 > default false. The query param carries an explicit off-state (?debug=0) so localhost prod-posture can be smoke-checked locally. Debug fixtures keep hard-coding debug: true in boot() — the BootOpts flag continues to override is_dev() entirely.
  • Forge version: v0.6.0, single release. The is_dev behaviour flip is a semantics change → minor bump (pre-1.0), and the phase-2 docs/JSDoc/HUD-anchor work rides the same release to avoid two npm publishes. No API renames in this release — naming strays are documented now, renamed at the Phase-8 v0.6-alignment per the audit's no-breaking-changes-pre-Phase-8 constraint (the debug default is a behaviour change, sanctioned explicitly by the audit's "safer default story").
  • Forge debug stats HUD moves to bottom-left — resolves the progress HUD collision globally (SSoT: fix once in forge, not N per-game offsets). Dev-only surface, so not a player-facing break.
  • HUD placement contract: top-left = player vitals (HP, XP), top-right = goal/timer/counters, bottom-left = reserved for forge debug stats (dev only), bottom-right = reserved. Player-facing text is Press Start 2P at 8px grid multiples (pixel recipe); debug overlays keep the crisp mono recipe.
  • Juice must not consume ctx.rng. Flash/particle systems added in phase 6 use a decorative RNG seeded from time.tick (module-local, never snapshotted) and spawn entities excluded from every world-hash projection — so replays stay green with NO re-record. Adversary checklists enforce this. If a coder finds this impossible for a given effect, the effect moves to that subsystem's rng-batched phase (7/8) instead of being hacked in.
  • rng-batching: each subsystem's rng-shifting changes (shell FSM deferring setup, spawn grace, menu-over-scene) land in exactly one phase so its replay fixture is re-recorded exactly once: bestiary/dungeon-walk/loot in phase 7, arena/progress in phase 8. Arena's menu-over-scene (spawning the arena behind the menu) shifts rng timing, so it is deliberately pulled OUT of the phase-5 visual sweep and into phase 8.
  • Shell contract scope per game: menu state is mandatory everywhere (title + controls + start prompt); won/lost states only where a win/loss condition exists (arena: has both; bestiary: survive-60s won / death lost; progress: dead-screen becomes lost + gains menu; dungeon-walk and loot: menu only, no fabricated win state).
  • Perk button labels: drop the "N. " text prefix from the label string; render the keycap hint as a separate small Text under/beside the button. Fixes the "2." orphan-line wrap without fighting wordWrap.
  • Template ships a scenario test, not a recorded replay — recorded fixtures would need re-recording on every convention change, defeating the living-template point. Seed-helper scenario tests (per docs/persistence-replay.md patterns) assert determinism without a recording.
  • Underscore exclusion convention: directories matching subsystems/_* build + test + typecheck normally but are skipped by the Pages aggregation step and never listed on the hub.
  • fps-counter anomaly is an investigation task, not a promised fix — all subsystems sit on the same forge ^0.5.4, so "version drift" is unlikely; if the root cause is forge-side (uncapped ticker vs counter mis-measure), the fix lands in the forge backlog (out-of-scope here) rather than blocking this pass.
  • Page-vs-integrate gate: no net-new pages/nav anywhere in this plan (see alternatives section). Hub changes integrate into the existing landing.
